Claude Code 在提示词里加禁令，原创游戏项目被一起拦下

NO.01 · AI coding · 行为约束

Claude Code 加了禁止复刻游戏的两句话，原创项目也被拦下

AI coding系统提示词拒绝执行误判成本
事件简述

10 月 27 日前后，Claude Code 通过服务器下发的标志 tengu_heron_brook 增加了一条规则，原文为：可以构建原创游戏、某一类型的游戏、以及用用户自己的设计和素材做的游戏；不要构建对某个既有游戏的重制，即使改名或声称原创也不行。这条规则没有对应的关闭开关。Anthropic 技术人员 Addy Osmani 在回应博主 chasm 时确认，团队在 Opus 5.5 上的 Claude Code 提示词里加了两句话，把 Claude 引离复刻他人具体游戏的行为，理由是借助 Claude 实施侵权违反使用政策，原创、类型化与自有素材的项目应当继续可用。

背景是 9 月 22 日发布的 Opus 5.5 让逆向与移植的门槛骤降：有人在浏览器里跑起《GTA 5》《使命召唤》，被破解的 PS5 上跑起《光环 2》与《塞尔达：旷野之息》；有用户用一句提示，不到两小时做出功能完整、可玩的宝可梦克隆。独立工作室 Alliance Arts 为此取消了新游戏的公开试玩，担心试玩内容被喂给模型后抢在正式版前上线山寨品。禁令落地后，Claude Code 的 GitHub issue 页面出现大量抱怨：开发者称自己写原创游戏写到一半被以「疑似复刻现有游戏」为由拒绝，给桌游打补丁、复现常见游戏机制的请求同样被挡。

关注理由

这条约束落在系统提示词与服务器下发的标志里，行为边界不可枚举、不可版本化、也没有关闭入口。对把 agent 放进自动化流水线的团队，模型拒绝执行变成一类新的失败源，报错信息是意图判断而不是技术错误，重试与回退都无从下手。

可操作的部分有三点：把这类策略判定当作外部依赖，对拒绝率与拒绝原因单独打点；在生成物上保留素材来源与命名记录，便于事后区分原创与复刻；对必须复现某种机制的合法需求，把任务拆到不含上下文的纯技术描述，让判定发生在明确的范围内。

NO.02 · AI coding · 长周期协议

上海人工智能实验室把编码 agent 拆成规划、开发与独立验收三个角色

AI coding多轮迭代证据状态回归
事件简述

上海人工智能实验室提出 Harness-of-Harness（HoH），把已有编码 agent 组织为反复执行的规划、开发与独立验收流程。Project Planner 依据产品需求、当前代码与上一轮证据选定一组任务，要求范围小到能定位故障、功能完整到能按可观察行为验收；Developer 从现有项目继续开发并拥有修改产物的权限；QA Tester 检查被冻结的候选版本，结合黑盒交互与白盒源码、配置、日志检查记录每项要求的证据与回归，且不能改动正在验收的产物。三个角色是同一 Harness–Model 配置的三次独立调用，靠提示词、输入上下文与运行权限区分。

轮次之间保留两类状态：Artifact State 记录当前源码、资源、配置与元数据，Evidence State 记录测试观察、已验证行为、未满足要求与待处理故障。计划与报告落在文件系统，先暴露分类索引再按需读取，避免把全部历史塞回上下文。实验覆盖 GameCraft-Bench 45 项、FrontierSWE 15 项与 ProgramBench，三种 Harness–Model 组合下 HoH@3 汇总指标均高于单轮基线，三轮迭代平均相对提升 52.25%。在 Codex 加 GPT-5.5 的 GameCraft-Bench 对照中，同为三轮，HoH 得 71.52 分，沿用原会话的 Vanilla Continuation 得 58.24 分；HoH 两轮约用 567 万 token 得 64.84 分，后者三轮约用 633 万 token 得 58.24 分。

另有一个连续 70 轮的单人 FPS 项目，从产品需求文档与空项目起，用 Codex CLI 加 GPT-5.6-Sol 与 Godot 开发。70 轮共记录 81 个问题，关闭 65 个、未解决 16 个，其中 17 个问题关闭后再次打开。

关注理由

长任务里真正难的是需求遗漏、重复劳动与回归累积：项目状态不等于最新代码，哪里没实现、哪次修复为什么失败，都散落在早期对话里。论文把这几个失控点转成可检查的工程约束，收益来自协议而不是模型，同一模型换运行方式就能拿到差别。

落到工程基础设施上，Planner 对应划定增量与验收条件，Developer 改 Git 工作区，验收角色接 CI、运行时检查与交互测试，issue 与版本历史承担回归追踪。需要注意「独立验收」只是流程独立与上下文隔离，三角色同模型仍共享知识盲区；70 轮案例的 17 次重开说明长周期自主开发仍会破坏已经验证过的功能。

NO.03 · 具身智能 · 评测协议

星衍智能的通用具身 Harness 在零样本协议下领跑 RoboDojo

具身智能零样本在线恢复跨本体
事件简述

星衍智能发布通用具身 Harness 框架 Auriga，把物理感知、动作表达、执行验证与任务状态管理整合成统一交互系统，让大语言模型在陌生任务中自主规划、执行并在线恢复。感知侧融合三维重建、视觉分割与机器人运动学，把图像转成带真实物理尺度、可查询可验证的空间信息；执行侧所有动作经统一网关走预演、执行验证与恢复三步，偏差超出容限时截停后续动作并返回偏差位置；记录侧留存模型意图、规划轨迹、实际运动与执行结果，上下文压缩后关键任务状态仍在。

评测以 GPT-6 Astra 为基础模型，采用严格零样本协议：不针对测试任务与布局预调优，所有任务共用同一套冻结的 Harness；不提供成功轨迹、视频演示或任务专用代码模板；每个案例只正式执行一次，中途抓取失败或受阻也必须从当前物理状态继续。RoboDojo 覆盖泛化、精细操作、长程、记忆与开放五类共 42 项任务，3 个随机种子共 6300 个回合，Auriga 取得平均成功率 57.74% 与过程评分 64.00，两项均列榜首，记忆类任务成功率 92.99%；布局随机化后的综合指标 G 为 46.3，领先第二名 2.4 分。迁移到家居移动操作基准 RoboCasa365 Target50 后，本体换成搭载 Franka 单臂的移动机器人、场景换成 10 个未见过的厨房，50 项任务 250 个回合总体成功率 73.2%，单技能 92.2%，最长 15 个子任务的组合任务 62.5%。

研发过程中 Harness 迭代 13 次，把不同任务暴露的共性问题逐步转成可复用的感知、控制与验证机制，RoboDojo 42 项任务的平均评分从第 4 版的 45.5 提到 64.0，成功率从 36.2% 提到 57.7%，评测前冻结后在另一类本体上检验复用。

关注理由

把「机器人自我进化」拆成三层看得更清楚：L1 反复重置环境为单个任务找更优解，L2 在一次连续执行中在线适应，L3 把跨任务反复出现的物理难题沉淀为通用工具与控制原语。只有 L3 的改进能被后续不同任务调用，也才谈得上迁移。

对做机器人系统的团队，这条路线把投入放在执行接口、轨迹预演、偏差截停与失败记录上，模型可以换，harness 的改进留得住；零样本协议把评测从反复刷题拉回一次执行，57.74% 的成功率因此更接近真实陌生场景下的水平。边界同样清楚：全部结果来自仿真，精密装配、复杂接触与长程操作仍是短板。

NO.04 · 具身智能 · 场景经济性

红旗连锁终止便利店机器人售货，研发投入约两百余万元

具身智能零售场景概念验证成本结构
事件简述

红旗连锁公告称，机器人无人售货系统暂未达到大规模商业化落地标准，基于投入产出比等考量，拟终止该系统研发，转为 24 小时云值守业务的规模化运营。项目启动时公司曾表示已完成实验室环境下的软硬件测试，样机预计当年 5 月下线，同时提示实验室环境与实际场景差异很大、距离面向消费者销售尚有距离；16 个月后等来的是终止公告。据接近项目的人士，机器人拿不稳夏季结水珠的玻璃瓶冷饮、经常摔碎，复杂包装商品也无法稳定拿取；便利店货架间过道窄，周围还有顾客与店员走动。

公司未披露该项目具体投入，2025 年年报显示研发费用约 286.68 万元，而此前财报并未公示研发费用，据此推断项目支出大体在这个量级。行业内并不意外：一位从业者的说法是，如果两百多万元能解决零售机器人，具身公司就没有存在价值。

机器人零售仍在扩张：全国已有超过 100 个机器人零售仓或零售布局，分布在 30 余座城市，十余家具身公司在做售货、现制饮品、药房拣选与门店导购。真实运营的状态是，零售仓 SKU 只有几十种，顾客扫码下单后机器人只承担移动到货架、夹取、放到窗口这一段，全程 20 多秒，且每天早 10 点到晚 10 点需要人值守补货、充电、报修；单台零售机器人售价近 70 万元，业内人士估算单仓成本近百万元。有从业者判断，文旅景区与城市地标能占到这类落地的六到七成，零售仓的复购率很低，实质更接近文旅项目。

关注理由

零售被当作「展示度高、容错率高」的中间形态，恰好暴露了当下的供需方向：本体公司需要场景，场景并不急需机器人。示范点位的传播价值可以支撑一段时间的采购，但几十个 SKU 的销售额覆盖不了百万级硬件加人工值守，商业模式仍停在概念验证。

对做整机与场景交付的团队，这个案例给出的成本项很具体：抓取要按包装软硬与表面状态分类，玻璃瓶结露就足以让任务失败；门店地面、货架高度与间距没有统一标准，交付只能是逐店改造的打包方案而非标准机器人；替代一名店员的时间判断在二到五年。选场景时先算清单店营收与回本周期，比先谈泛化能力更有效。

NO.05 · 终端智能 · 系统入口

国行 Apple 智能接入千问，11 月 4 日随开发者 Beta 开放测试

终端智能系统级入口账号与授权端云分工
事件简述

10 月 31 日，苹果宣布首批 Apple 智能功能即将在中国推出，并与阿里巴巴合作，在部分体验中接入千问。这批功能自 11 月 4 日起随最新 iOS 开发者 Beta 版开放测试，12 月随 iOS 27.3 正式版面向中国用户推出；其他平台的支持待必要审批后推出。这是 Apple 智能自 2024 年发布以来国行版本第一次实质性落地，此前苹果智能已于 7 月 15 日通过生成式 AI 服务备案。

首批能力集中在基础高频场景：实时翻译整合在信息、FaceTime 与电话中，支持 AirPods 4 与 AirPods Pro 2 及后续机型做面对面翻译；写作工具提供改写、校对与摘要；视觉智能通过摄像头识别身边物体与场所；照片可消除干扰对象、用自然语言搜索、按描述生成回忆影片；另有智绘表情、优先邮件、邮件摘要、智能回复、通知摘要、首要通知，备忘录与通话转写的文本可自动生成摘要。本次更新不包含 Siri AI 与 WWDC 2026 上宣布的其他下一代功能。

千问以系统级扩展的形式接入三个入口：Siri 处理复杂问答与针对照片、PDF、演示文稿的提问；系统写作工具新增「千问创作」；视觉智能可选「询问千问」。用户可以自主选择是否开通，通过 Apple 登录或千问账号登录，可以决定何时使用、分享哪些信息，请求与生成的回复不会被阿里巴巴用于模型训练。集成范围目前仅限 iPhone。

关注理由

这是国内第一次把第三方大模型装进手机操作系统的原生入口。分工也一并写明：苹果自建模型负责基础能力，千问接管复杂文本与图像理解、跨文档问答与从零生成，两者是系统级扩展关系而非替换。

对做终端智能的团队，入口位置、账号体系与授权颗粒度都由操作系统决定，第三方应用能调用的位置被收进系统面板，绕过系统的独立 App 路线空间变窄。逐次征得同意、明确数据不用于训练、可随时关闭，这套口径会成为同类合作的默认条款；把系统级入口当作分发渠道来规划，比把它当作一个模型接入点更贴近实际。
