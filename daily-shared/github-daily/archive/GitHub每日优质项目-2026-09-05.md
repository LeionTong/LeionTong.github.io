**1. pdf-inspector**（firecrawl/pdf-inspector）｜⭐ 18,822（近 30 天 +9,431）｜Rust · MIT · 最近提交 2026-09-03 · v1.15.0（2026-08-17）
- 一句话定位：Rust 写的 PDF 分类与抽取库，先判断要不要 OCR，再决定怎么抽。
- 解决什么痛点：文档管线默认对所有 PDF 上 OCR，官方口径约 54% 的 PDF 其实不需要，这笔钱纯属浪费。
- 谁会付钱 / 怎么收费：RAG、合同审查、票据与财报处理团队；省下的是 OCR 服务调用费，库本身 MIT 免费，可变现的是集成部署与托管管线。
- 规模化判断：凡有 PDF 入库环节的行业都通用，Rust / Python / Node / WASM 四种 binding，接入完全标准化。
- 边际成本：低 —— 纯客户端库，无服务端、无 GPU，客户自带算力。
- 快速验证：
  ```bash
  pip install pdf-inspector
  ```
  ```python
  import pdf_inspector
  r = pdf_inspector.process_pdf("任意一份.pdf")
  print(r.pdf_type, r.markdown[:200])   # 用真实合同/财报跑一次，看分类是否命中
  ```
  官方 Quick start → https://github.com/firecrawl/pdf-inspector#quick-start
- 风险与坑：212 个 open issue 偏高；benchmark 由 Firecrawl 自行跑分（opendataloader-bench 语料 200 份 PDF），需在自己的语料上复测；它只解决「分类 + 抽取 + 选择性 OCR」，复杂版面还原仍要兜底方案。
- 评分：商业化 5 · 规模化 5 · 边际成本 5 · 验证速度 5 · 成熟度 4 → **加权 4.90**

**2. celld**（denoland/celld）｜⭐ 4,491（近 30 天 +4,433）｜Rust · Apache-2.0 · 最近提交 2026-08-28（v0.4.0）
- 一句话定位：把 Cloudflare Workers 与 Durable Objects 搬到自己机器上跑的自托管守护进程。
- 解决什么痛点：Durable Objects 这套有状态模型好用，但强绑 Cloudflare，迁移成本几乎等于重写。
- 谁会付钱 / 怎么收费：被 CF 绑定、或受数据出境约束的团队；Deno 官方走托管变现，第三方可做自托管运维服务与迁移交付。
- 规模化判断：状态型边缘应用是通用需求，客户群等于「所有在用 Durable Objects 的人」，可打包成标准托管套餐。
- 边际成本：中 —— 纯软件，但托管形态需按 cell 提供机器与对象存储，成本随客户量走。
- 快速验证：
  ```bash
  curl -fsSL https://celld.dev/install.sh | sh
  celld --help
  ```
  备一个 S3 兼容桶，按 https://celld.dev/docs 起单节点，部署一个最小 Wrangler 项目，看 cell 是否被正确持有。
- 风险与坑：v0.4.0 未到 1.0，ownership 与 LTX 复制协议复杂，排障门槛高；需 esbuild 与对象存储；单节点写入要等桶确认，性能明显弱于多节点。
- 评分：商业化 4 · 规模化 4 · 边际成本 4 · 验证速度 3 · 成熟度 3 → **加权 3.75**

## 一、今日首选

**firecrawl/pdf-inspector**。它是今日唯一五维无短板的标的：MIT、纯客户端库、一条 `pip install` 即可验证，且省下的钱能被精确算出来——约 54% 的 PDF 根本不需要 OCR。替代账越具体，成交阻力越小。

## 二、组合观察

今日五条里有四条在做同一件事：把按次或按席位计费的外部依赖，换成自有可控的软件栈——OCR 调用（pdf-inspector）、Durable Objects（celld）、MCP 接入（Jarvis Registry）、Agent 推理（Magnitude）；Shippie 则是用 Agent 直接顶掉按席位收费的 SaaS。

信号很清楚：**开源商业化的主战场已从「模型能力」彻底转向「账单项替换」——谁能把客户现有账本上的某一行换成自有软件，谁就拿到定价权。**

第二层信号：五条全部是 MIT 或 Apache-2.0，License 不再是商业化障碍，竞争完全落在谁先把替代账算清楚。
