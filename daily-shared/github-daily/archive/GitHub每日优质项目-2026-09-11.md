**1. Zvec**（alibaba/zvec）｜⭐ 15,885（近 7 天 +192；近 30 天 未获取到）｜C++ · Apache-2.0 · 最近提交 2026-09-10

- 一句话定位：进程内嵌入式向量数据库，像 SQLite 一样以库的形式嵌进应用，不起服务、不做配置。
- 解决什么痛点：只要上向量检索，默认路径就是起一套 Qdrant / Milvus / Weaviate，或买 Pinecone 的托管账单——中小规模为这点能力付了整套运维与云费用。
- 谁会付钱 / 怎么收费：需要本地或端侧检索的 SaaS、Agent 应用与边缘设备厂商；变现走企业支持、托管服务与索引调优。Apache-2.0 无授权障碍。
- 规模化判断：跨行业通用，交付就是一个库依赖（pip / npm / cargo / pub），无实施、无驻场。
- 边际成本：低 —— 纯库无服务器进程，每新增客户零增量成本。
- 快速验证：`pip install zvec`，照 README 的一分钟示例建集合、插入两条向量、跑一次 `query(topk=10)`。
- 风险与坑：仍是 0.x（v0.7.0，2026-08-24）；多进程可并发读但写为单进程独占；赛道拥挤（FAISS / LanceDB / Chroma），差异化只能落在端侧与移动端 SDK、以及 zvec-grep 这条 Agent 检索入口上。

**2. App Store Connect CLI**（rorkai/App-Store-Connect-CLI）｜⭐ 7,182（近 30 天 +1,495）｜Go · MIT · 最近提交 2026-09-10

- 一句话定位：`asc` 一条命令管完 App Store Connect——TestFlight、构建、提审、签名、截图、订阅与分析，CI 与 Agent 都能直接调用。
- 解决什么痛点：iOS 发版至今高度依赖网页控制台点选加 fastlane 脚本拼装，换人即断档；App Store Connect API 原生难用，团队各写各的封装。
- 谁会付钱 / 怎么收费：移动团队与外包交付商为「发版不必再人肉值守」付费；可变现形态是把 `asc skills`（25 个已审核 Agent 技能）打包成发版自动化交付与运维托管。
- 规模化判断：凡有 iOS / macOS 应用的组织都通用，交付就是 Homebrew 装一个二进制加一份配置，可完全标准化。
- 边际成本：低 —— 单二进制自包含，无服务端、无 GPU、无专有依赖。
- 快速验证：`brew install asc && asc version && asc --help`，确认二进制可用后再按 README 用 API key 走 `asc auth login`。
- 风险与坑：写操作需要 Apple 开发者账号与 .p8 密钥，首次验证卡在权限而非代码；强绑定 Apple 生态，平台政策变动直接改写可用面；同类封装（fastlane）心智已占稳，切动力取决于 Agent 技能这一层是否真能省人。
- 评分：商业化 4 · 规模化 4 · 边际成本 5 · 验证速度 4 · 成熟度 4 → 加权 4.20

- 解决什么痛点：把 Agent 从 demo 推到生产要自己补齐崩溃恢复、状态持久化、RBAC 与多机器调度，这部分每家都在重复造。
- 谁会付钱 / 怎么收费：已有明确收费模式——Omnara Cloud 按托管收费，开源版可私部署；自托管部署做交付与运维支持同样成立。
- 规模化判断：凡要把 Agent 交给内部员工或外部客户用的团队都是受众；交付为 Docker Compose 一套，状态落在 Postgres，不依赖现场定制。
- 边际成本：低 —— 纯软件控制平面，沙箱可接 Blaxel / Daytona / Modal 或客户自己的机器，无硬件投入。
- 快速验证：`git clone https://github.com/omnara-ai/omnara.git && cd omnara && docker compose -f compose.yaml --profile app up -d`，本地认证邮件写在 `docker compose logs api` 里，无需先配邮件服务即可开 8000 端口。
- 风险与坑：版本仍在 0.1.x（omnarad-v0.1.19）；沙箱依赖第三方供应商即意味着成本与可用性不完全自控；「Agent 运行平台」赛道玩家密集，客户往往先自研一版再决定买不买。

- 一句话定位：React Native 的自托管 OTA 更新方案，走官方 Expo Updates 协议，服务端、存储与 CDN 全在自己手里。
- 解决什么痛点：CodePush 关停后 RN 热更新出现真空，商业方案（EAS Update 等）按 MAU 与流量计价且锁定厂商；自建又要从差分、灰度、回滚做起。
- 谁会付钱 / 怎么收费：中大型 RN 应用为「更新链路不落在别人家」付费；可变现形态是自托管交付、灰度与回滚策略配置、以及行业合规版本。
- 规模化判断：所有 RN 应用通用，一套 CLI 加一套服务端即可复制，多应用共用同一 dashboard。
- 边际成本：低 —— 插件式存储接 AWS S3 / Cloudflare R2 + D1，带宽由客户自付，每新增客户无边际投入。

- 风险与坑：当前主线是 v1.0.0-rc.14（v1 尚未正式发布），rc 期间配置格式仍可能变；只服务 React Native，市场天花板由 RN 生态决定；自托管意味着客户要自己承担更新事故的责任与回滚压力。

**5. RunsOn**（runs-on/runs-on）｜⭐ 1,327（近 30 天 未获取到）｜MIT · 最近提交 2026-09-10

- 一句话定位：跑在客户自己 AWS 账号里的 GitHub Actions 控制平面，每个 job 起一台全新 EC2 runner，用 CloudFormation 或 Terraform 一套栈装完。
- 解决什么痛点：GitHub 托管 runner 按分钟计价且机型固定，CI 账单随团队规模线性涨，还拿不到 GPU、ARM64 与自定义镜像。
- 谁会付钱 / 怎么收费：已有明确定价与授权（Flex / Fleet 共用一份 license）；省的是公开可比的差价——2 vCPU Linux $0.0009/min 对 GitHub 托管 $0.0060/min，T4 GPU 差最高 13 倍。
- 规模化判断：凡用 GitHub Actions 的工程团队都通用，交付是一个 IaC 栈加 runner 规格目录，平台团队可统一发布。
- 边际成本：低 —— 软件控制平面，算力与账单在客户 AWS 账号内，供应商无需为新增客户投入资源。
- 快速验证：按 runs-on.com/installation/flex 起一个 CloudFormation 栈，把 workflow 里的 `runs-on:` 改成 `runs-on=${{ github.run_id }}/family=c8a+m8a/cpu=4/ram=8+16/image=ubuntu24-full-x64` 跑一次。
- 风险与坑：强绑定 AWS，非 AWS 客户直接出局；验证需要一个可用 AWS 账号与 IAM 权限，30 分钟略紧；GitHub 官方随时可能调整托管 runner 定价，价差是动态目标。
- 评分：商业化 5 · 规模化 4 · 边际成本 4 · 验证速度 3 · 成熟度 4 → 加权 4.15

## 一、今日首选

**alibaba/zvec**（加权 4.60）。它把一整块云服务账单压缩成一个库依赖——不需要说服客户改架构、加运维或新建账号，`pip install` 即完成交付动作。阿里集团内部已生产验证，Apache-2.0，且端侧与移动端 SDK 是现存方案普遍没覆盖的切口。

## 二、组合观察

五条里没有一条在卖模型能力，卖的全是「把某项已经付了多年的固定成本换成自己掌控的形态」：向量检索账单、发版人力、Agent 托管费、OTA 更新服务、CI 分钟费。其中三条（asc、hot-updater、runs-on）集中在构建与发布流水线上——这一段最容易成交，因为单价是公开可查的（GitHub 每分钟报价、EAS Update 的 MAU 计价、发版值守的人天）。

两条主流项目都不做「另一个平台」而是做「嵌进去」：zvec 是库不是服务，asc 是 CLI 不是控制台。不要求客户迁移工作流，是当下开源替代最省力的进入姿势。

## 三、暂不建议碰

1. **Wei-Shaw/sub2api**（⭐ 41,171，近 30 天 +4,895，Go · LGPL-3.0）— 把 Claude / OpenAI / Gemini / Grok 订阅聚合成统一中转并支持拼车共享分摊成本。热度真实，但共享订阅直接撞上游服务条款，交付给客户即等于把对方的封号风险写进自己的 SLA；LGPL-3.0 也限制二次分发形态。
2. **ayghri/i-have-adhd**（⭐ 38,560，近 30 天 +18,245，MIT）— 本质是让编码 Agent 别把答案埋起来的提示词技能。无产品形态、无收费入口、复制成本为零，fork 一份即等价，热度来自安装量而非付费意愿。
